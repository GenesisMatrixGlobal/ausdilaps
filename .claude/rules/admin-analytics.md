# Command Centre analytics: API spend, portal usage, real-user speed

Moved verbatim from the root `CLAUDE.md` §3 on 2026-10-26 so it loads only when working on these files. Project-wide rules (Supabase refs, local dev writes to production, guardrails) stay in the root file.

- **API spend on the dashboard (BUILT 2026-09-14).** `api_calls` table (migration `0018`, ✅ **APPLIED to Sydney 2026-09-14** via the SQL editor in the Browser pane — "Success. No rows returned", and `api_usage_summary` answers through PostgREST), `lib/api-usage.ts` (writer), `lib/admin/api-usage.ts` (reader), `/admin/usage` (page), an "API spend · month" tile on `/admin`. Rhys wanted a top-down monthly view of what the tools cost, split per tool, with a total — and Google can't split a bill by tool (one key for everything), nor can Anthropic, so we count at the point of each call.
  - **ONE row per outbound paid call**, written with `void recordApiCall({...})` right after the `fetch` at every Google and Anthropic call site (15 of them: geocoding ×4 files, Places autocomplete/details, Street View metadata, Static Maps — **one row per TILE**, Directions, and every `api.anthropic.com` call — OCR ×2, site-plan label vision, floor plan, tender classify, knowledge indexing). Priced at LIST in `GOOGLE_CENTS_PER_REQUEST` and `ANTHROPIC_USD_PER_MTOK` (Anthropic from the `usage` tokens each response reports, cache reads at 0.1x, writes at 1.25x). **Google's free monthly allowance IS applied — at READ time** (`applyGoogleFreeAllowance` in `lib/admin/api-usage.ts`, `GOOGLE_FREE_REQUESTS_PER_MONTH`: every API this app calls is an Essentials SKU with 10,000 free requests a month on standard pay-as-you-go; Rhys confirmed no negotiated rates, 2026-09-14). Rows store LIST cost so a price change re-prices history; the reader bills only the requests past the allowance, account-wide per API, split across tools in proportion. So the page shows what the invoice SHOULD read (Anthropic exact, Google after free tier) with the list-price figure alongside — and the standing instruction is to compare against the first full month's invoices once.
  - **Attribution is by the STAFF PAGE, read off the Referer** (`/staff/<dept>/tools/<slug>` → slug), so no route has to say which tool it belongs to and the two shared routes (`/api/places/*`, `/api/maps/*`) attribute correctly. Same-origin fetches carry the full URL under our `strict-origin-when-cross-origin` policy. Jobs with no page name themselves: `tender-watch` (cron) and `knowledge-index` (postbuild + manage page). Verified locally: a search on Building Markup logged `places_autocomplete` and `places_details` with `tool: "site-markups"`.
  - **Production only** (`VERCEL_ENV === "production"`, same gate as the other counters). `API_USAGE_LOG=1` in `.env.local` prints the would-be row to the dev server log instead — that is how attribution is checked without writing to the live table. `lib/api-usage.ts` deliberately imports `next/headers`, `next/server` and the admin client DYNAMICALLY: `lib/knowledge/ai.ts` and `lib/tenders/classify.ts` run under tsx and the cron as well as in routes, and a static `server-only` import would break them.
  - Totals come from the SQL function `api_usage_summary(since, until_at)` (grouped by tool/provider/api) so the page never pages raw rows — PostgREST caps a select at 1,000, which a busy month would pass. Months are BRISBANE calendar months.
  - ArcGIS (the state cadastres) is in the schema as a free provider but is NOT instrumented yet — six fetch sites, zero dollars; add it if a spike there ever matters.
- **Who is using the portal (BUILT 2026-09-18, Rhys: "basic tracking so we can see who's actively using things and who's not").** Each card on `/admin/staff` carries one muted line: **Last active** (the later of `profiles.last_seen_at` — written every 15 min by `touchLastSeen()` — and auth's `last_sign_in_at`, because a magic-link session lasts weeks so sign-in alone calls a daily user idle) and **N tool uses · 30d** with a per-tool breakdown; `/admin/tools` rows gained a "Used by Name 9 · Name 3" line. Migration **`0020_tool_usage_user.sql`** adds `tool_usage.user_id` (nullable, `on delete set null` so a leaver's history stays on the tool's count) — the column 0008 deliberately left off; 0020's header says why that changed. ⚠️ **NOT YET APPLIED** — paste it in the SQL editor. Until then `recordToolUse()` retries without the column and `fetchUsageRows()` selects without it, so counting carries on exactly as before and every row shows as "unattributed". `recordToolUse(slug, userId)` gets the id from `isStaff()` (now keeps the user instead of `!== null`), and directly in the site-snap and transcribe routes. **Games are excluded from a person's count** (same rule as the `/admin` headline) — a card reading "40 tool uses" for someone who only plays Site Snap misleads exactly the reader it is for. Both readers derive from ONE `cache()`d 30-day fetch (`fetchUsageRows`), so the per-tool and per-person figures on `/admin/tools` are counted from the same rows.
- **Real-user speed on the dashboard (BUILT 2026-09-14).** `web_vitals` table (migration `0016`), `lib/web-vitals.ts`, public collector `POST /api/vitals`, client `components/marketing/web-vitals-reporter.tsx` mounted in the root layout. `/admin` → Site health now pairs Google's LAB scores (PageSpeed API, daily) with FIELD data from real visitors: LCP / INP / CLS at the **75th percentile** over 7 days, plus the slowest pages.
  - **ONE ROW PER PAGE VIEW, not one per metric.** The five vitals land at different moments (TTFB/FCP on load, LCP on the biggest paint, CLS as the layout settles, INP only on a real interaction), so the client accumulates and posts once via `navigator.sendBeacon`. Five rows per view would be 5x the writes and make every query a pivot.
  - **Sends on `visibilitychange` → hidden, NOT `beforeunload`.** iOS Safari freezes and reuses a page rather than unloading it, so beforeunload often never fires — which would drop the mobile half of the sample, exactly the half most likely to be slow. A `sent` ref keeps tab-switching from re-posting.
  - Metrics are NULLABLE and partial rows are KEPT: a visitor who reads and leaves produces no INP, and discarding those rows would bias the sample toward long interactive visits.
  - The route is public by necessity (a visitor has no session), so it is bounded hard: pathname-only regex (a query string is REJECTED, not cleaned — the samples access code lives in one), 600s ceiling per metric, bot-UA filter, and a row with no metric at all is dropped so the sample count stays an honest denominator. No user, no IP, no session — nothing to join back to a person.
  - ⚠️ **The Supabase client RETURNS errors, it does not throw.** `recordVitals`, `recordPageView` and `recordToolUse` all awaited an insert without reading `error`, so every write failure — missing table, bad column, revoked key — looked exactly like success. All three now `if (error) throw error` into their existing catch. This is why a missing `page_views` table logged nothing for the whole gap before `0015` was applied.
