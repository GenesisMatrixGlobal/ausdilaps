# Cover Photo Generator (CVR)

Moved verbatim from the root `CLAUDE.md` §3 on 2026-10-26 so it loads only when working on these files. Project-wide rules (Supabase refs, local dev writes to production, guardrails) stay in the root file.

- **Cover Photo Generator (`cover-photo`, code `CVR`) — REPORTS department, BUILT 2026-09-16.** The front-page image for a report: type an address, press Generate, and the property's cadastre boundary is drawn in GREEN on a live aerial, auto-framed; press Send to Salesforce and the PNG is filed in Box and its link written to `Survey__c.Cover_Photo_URL__c`. `components/tools/cover-photo/*`, `lib/cover-photo/*`, `app/api/cover-photo/{parcel,render}`, `app/api/salesforce/cover-photo/{resolve,upload}`.
  - **A deliberate repurposing of Markup and Measure, NOT a tab on it.** It reuses that tool's cadastre pipeline (`resolveStandardMarkup`, whose `neighbours` are discarded — a cover photo shows ONE property), its tiled Static Maps renderer and its vertex handles, and throws away everything that serves a quote rather than a report: no lots, no line items, no numbered badges, no legend, no north arrow, **no measurements**. The boundary is always GREEN and always an AREA.
  - **The output SIZE is a toolbar picker (2026-09-22): 600x442, 900x663 or 1200x884** — `COVER_SCALES` [1, 1.5, 2] times the report template's box (`COVER_BOX_WIDTH`/`HEIGHT`), default 2x. Bigger is free at Google's end: the frame is already fetched at ~1500-2500px and downscaled, so a larger output just throws away less of it. ⚠️ **Every scale must land on WHOLE pixels and the same aspect** — the box is a multiple of 2 for that reason, and `check:cover` asserts both for each entry, because a half-pixel size turns the final resize into a fractional stretch that is invisible on an aerial photo. `COVER_ASPECT` is derived from the BOX, so **picking a size can never change what is in frame** — only the last `sharp.resize` reads the scale. The picker sits beside Download .png and governs **both** it and Send to Salesforce: they share one `renderImage`, so the downloaded file and the image on the Survey can never come out different sizes. ⚠️ `scale` is in `renderImage`'s dependency list — `SyncCoverPhoto` holds that callback and calls it at upload time, so a stale one would file the previous size.
  - ⚠️ **`coverFrameBounds()` pre-compensates for the attribution pad, and that is the whole trick.** `planTiles()` frames `ATTRIBUTION_PAD_PX` (20 logical px) of EXTRA ground along the bottom for Google's attribution bar to sit on — cropping or shrinking that bar is exactly what the Maps Platform terms forbid. So a box whose GROUND is 600:442 renders at `w x (w/A + pad)`, and the resize to 600x442 becomes a vertical squash nobody would ever spot on an aerial photo. Shortening the ground span by the pad puts the RENDERED PLAN on the target aspect, so the resize is 1:1. `npm run check:cover` asserts that across six parcel shapes at five latitudes (Mercator's scale varies with latitude, so one test city proves nothing); the bar is RELATIVE aspect error under 0.5%, not absolute pixels, because planTiles rounds both axes up to even and a few pixels of drift is structural.
  - ⚠️⚠️ **THE TILER MUST NOT PLAN PAST `MAX_STATIC_ZOOM` (20), and it did for two weeks.** `planTiles` had its own `MAX_ZOOM = 21` while `buildStaticMapUrl` clamps every URL to 20 — **silently**. So each tile came back showing TWICE the ground it was planned for: the stitched frame repeated the same houses, and the outline, projected at the PLANNED zoom, was drawn twice too big over them. Reported from the field 2026-09-29 (Samantha, 34 and 38 Rainwood Street, Bracken Ridge — "even after drawing the boxes over the houses, it would still download like this"), and the screen was always right, because the live Maps JS map never goes through this path. **The constant is now exported from `static-map.ts` and IMPORTED by the planner** — one value, the CLAUDE.md two-places rule; `check:cover` asserts `plan.zoom <= MAX_STATIC_ZOOM` per case.
    - ⚠️ **It was LATITUDE-dependent, which is exactly why it got through.** The planner picks 21 when the frame fits 640px at zoom 20, and metres-per-pixel grows towards the equator: at the 78 m default it broke at **Cairns, Brisbane AND Sydney, and not at Melbourne**. Every visual export check had been done on Newport VIC and on a 90 m Dover Heights frame — both safe — and the Aspley QLD check measured the LIVE map's zoom (20.15), not the export's plan. **A northern-latitude EXPORT at the shipped default was never looked at.** One Zoom-out click (90 m) was enough to make it right, which is why it looked intermittent. Frames at 120 m or wider were never affected, so Building Markup / Measure (which frame from a ~150 m+ viewport) would only ever have hit it on an unusually zoomed-in export.
    - ⚠️ **Capping at 20 costs real pixels on a tight frame and that is CORRECT** — zoom 20 is where genuine AU satellite imagery stops. Cairns now bottoms out at a 1148px source, so the 1200px (2x) output is a ~4% upscale. `check:cover` asserts the source covers the SMALLEST offered size, not the largest, on purpose: the old "supersampled to 1200px" figure was fiction, since the zoom-21 request was clamped to 20 anyway.
  - ⚠️ **`sharp` applies `resize` BEFORE `composite`, whatever order you chain them in.** Doing both in one pass shrinks the frame to 600x442 first and then tries to paste the 2476px overlay onto it: *"Image to composite must have same dimensions or smaller"*. `render.ts` composites at full size, `toBuffer()`s, then resizes in a SECOND sharp call — which is also the better image, since the green outline is resampled with the imagery.
  - **The toolbar sits ABOVE the map** (Rhys, 2026-09-16). The map is the tall element on the page, so buttons under it fall off the bottom of a laptop screen by the time the drawing is scrolled into view.
  - ⚠️ **Google's own zoom buttons are OFF (`zoomControl: false`) and that is the fix for "+ goes in way too far".** Rhys reported it twice and both times it was Google's control, not the toolbar's: Google's steps to the next WHOLE zoom level, which with `isFractionalZoomEnabled` is a variable jump of up to 2x the ground (measured 1.34x from a fractional position), and it sits in the map's bottom-right exactly where you reach for a zoom. The toolbar's stepper was always moving one measured 1.15x step — verified by clicking each and measuring the frame. **Two zoom controls on one screen stepping by different amounts is the bug**; don't reinstate Google's. Cmd/Ctrl + scroll still gives free-form zoom. (Google leaves the buttons in the DOM at 0x0, so a `querySelectorAll('[aria-label="Zoom in"]')` still finds them — check `getBoundingClientRect()` before concluding they are on screen.)
  - **Picking an address GENERATES** (`generate(target)` takes the place as an ARGUMENT, because the dropdown calls it in the same tick as `setPlace()` where the new value isn't visible yet). Showing a map with nothing on it and waiting for a button press read as "something is broken" — there is nothing else a picked address could mean here. The button stays, as Regenerate.
  - **No map until an address is picked.** Mounting a Maps JS map is a billed Dynamic Maps load, and an empty map of Brisbane tells the operator nothing. It mounts on the address PICK rather than on Generate, so Google Maps is already loaded by the time the cadastre answers and the first frame lands without a wait.
  - **`COVER_DIM_OUTSIDE_PERCENT` (22) dims everything OUTSIDE the boundary, on the EXPORT *and* the live map.** In the export it is one SVG path, two subpaths, `fill-rule: evenodd`; on the map it is a second `google.maps.Polygon` whose outer ring carries the boundary as a reversed HOLE (Google only reads an inner path as a hole when it is wound opposite). The live copy exists because without it the preview showed a bright surround and the PNG a dimmed one — the preview/export drift this file calls the standing hazard on these tools, and Rhys hit it immediately ("I can't see the 22% overlay"). ⚠️ **The scrim's outer ring is a LOCAL box (`DIM_SPAN_DEGREES` 2), never the whole world.** A polygon spanning -180..180 renders DEGENERATELY in Maps JS: it reports the right paths, the right fill and `visible: true`, and paints nothing — verified by swapping the same polygon to a local box with everything else unchanged and watching it appear. Dimming the surroundings is what makes the shape pop; a uniform scrim knocks the green back by exactly as much as everything else. **Set it to 0 and the layer is skipped entirely — that is the whole undo.** ⚠️ The scrim FADES OUT over Google's attribution band with a gradient. The terms forbid obscuring that attribution, but simply stopping the rectangle short of the band leaves a hard horizontal step across the full width that is plainly visible on the finished image — checked by cropping the bottom 120px and blowing it up. The gradient does both jobs.
  - ⚠️ **The live map's WIDTH is capped at 760px, and that is load-bearing, not styling.** The width decides the zoom the default frame fits at — wider map, same 78 m of ground, deeper zoom. **The real ceiling is 20.5**, not 21: at 20.5 Maps JS stops scaling zoom-20 tiles and starts requesting zoom-21 ones, which often do not exist over Australia, so the map goes grey and only fills in once you zoom and it re-requests. That is what "it doesn't actually load the image properly until I zoom" was at 68 Mason St, Newport, on a full-width map fitting at ~20.8. **760px is the widest that keeps a 78 m frame under 20.5 at every Australian latitude** — Cairns is the binding case at 772px, Hobart would allow 1008px. Widen past 772 and northern QLD jobs start coming up grey. `maxZoom` stays 21 so the toolbar's Zoom control keeps working; the default frame simply never asks for more. The EXPORT is unaffected either way — it re-renders from the bounds through Static Maps and downsamples, so the PNG keeps its detail whatever the preview shows.
  - **The map is shown at the OUTPUT's size, not just its aspect.** That is what makes the tool what-you-see-is-what-you-get twice over — the operator frames the cover photo at 1:1, and the default frame fits inside the imagery ceiling. Verified live, including a shape running off the frame's edge on screen coming out clipped the same way in the PNG. **The frame is fetched at whatever detail the tiler can get (typically 2476x1824, 4 tiles) and downscaled**, so the result is supersampled rather than a soft 600px image asked for directly.
  - **Framing: `coverViewFor(ring, step)` = the parcel + 25% a side, with a `MIN_FRAME_METRES` (90) FLOOR on the width.** The margin alone is not enough on a suburban block — a 700 m² lot is ~15 m wide, and 15 m plus 25% a side is a 23 m frame with no street, no neighbour and no label in shot. Verified: 44 Eastern Ave, Dover Heights is a 13x36 m lot → a 78x57 m frame. (150 m/45% → 115 m/35% → 90 m/25% → 78 m; Rhys asked for one step tighter three times on 2026-09-16, each time after looking at real exports. `check:cover` asserts the FLOOR is honoured, not that two small lots come out identical — that stopped being true at 90 m, where a 45 m-deep lot drives its own frame.)
  - **`step` is the toolbar's Zoom control** (`ZOOM_STEP` **1.15** per click, clamped -6..+10; 1.3 was too big a jump on an already-tight default): it scales the finished frame, so it behaves the same on a block held at the metre floor as on a rural parcel where the margin dominates, and it re-frames around the BOUNDARY — Google's own +/- zoom the current centre, which after a pan stops being about the property at all. ⚠️ **The step is a REF, not state.** Two quick clicks land in the same React batch, so reading it from state made both handlers see the same stale value and the second click do nothing — verified, `-` `-` moved one step instead of two.
  - **Green (`COVER_GREEN` = `16a34a`, fill 38%) lives in `lib/cover-photo/style.ts`, deliberately NOT in `lib/kml/standard-markup/style.ts`.** It started lighter (`22c55e` at 28%) and was darkened on Rhys's call — the lighter fill washed out over pale roofs and concrete. Adding a colour to the markup path costs four coordinated changes (that file, BOTH schema enums, `colourKeys()`) plus regenerating `overlay-paths.ts` for a new legend label — which needs local macOS Arial Bold, because Vercel's runtime has no fonts and `<text>` renders blank. A cover photo has no legend, so it needs none of it. One hex constant.
  - ⚠️ **NO `styles` on the live Maps JS map** — legacy JSON styling silently breaks tile rendering on this API version (valid `getCenter()`, no log, no tiles). The SERVER render does pass `feature:poi|visibility:off` to the Static Maps API, which is a different API and unaffected: POI pins go, **road and suburb labels stay**, and they are half the point of the border.
  - **A cadastre miss is a normal outcome, not an error** — unlike `/api/kml/standard-markup`, which 404s. `/api/cover-photo/parcel` always 200s with `ring: null` and a plain-English note; the map centres on the geocoded point and the operator draws the boundary. Same for WA/SA/TAS/NT/ACT, which have no adapter. **The tool works everywhere; only the automatic half is QLD/NSW/VIC.**
  - **Salesforce: `Survey__c` (key prefix `a4F`) → `Opportunity__c` → `Opportunity__r.Link_to_Box_Files__c` → `4. Reports` → `Template Documents - Completed`.** All verified against the live org and the live Box tree on 2026-09-16. Field names are env-overridable (`SF_SURVEY_COVER_PHOTO_FIELD`, `SF_SURVEY_OPPORTUNITY_FIELD`); the relationship name is DERIVED from the lookup field (`__c` → `__r`) rather than being a second thing to configure. Uses the existing client-credentials `SF_*` app, **not** the dormant `SF_SURVEY_*` JWT app (that one is the Excel row importer and has no code). (`SF_SYNC_ENABLED` and the lead-form sync were deleted 2026-10-07.)
  - **One field, not five slots**, so `linkMarkupToLineItem` is the model: `alreadyFilled` is reported at resolve time, the checkbox relabels to "Replace the cover photo already linked to this Survey", and the server **re-reads the field at write time** and refuses without `replaceExistingLink` — so a stale resolve can never silently overwrite a colleague's link. A failed link is reported, **never rolled back**: the PNG is correctly filed in Box.
  - ⚠️ **The Box shared link is `access: "open"`, and that is REQUIRED, not a default to tidy up.** **FormTitan fetches this URL anonymously when it merges the report.** A `company` link answers an anonymous request with HTTP **200 and Box's LOGIN PAGE** — ~23KB of `text/html` where the merge expected a PNG — so the cover photo silently merges blank. Measured against a Site Markup link that merges today: that one is `open` and returns `200 image/png, 967KB`; the cover photo on `company` returned `200 text/html`. The cost is real and was weighed: an open link is readable by anyone holding the URL, which is the same exposure the Site Mark Up images already carry, the URL only travels in the Salesforce field and the merged report, and a cover photo is an aerial of a property carrying no personal data.
  - ⚠️⚠️ **`curl -I` IS NOT A VALID TEST OF THIS, and getting that wrong cost a whole wrong diagnosis.** A HEAD request against `box.com/shared/static/…` returns **404 for an open link and a company link alike**, which makes them look identical — it was used to "prove" scope didn't matter, and that conclusion was wrong. **Always GET and check the `content-type`**: `image/png` is working, `text/html` is Box's login page. And note the two halves are INDEPENDENT — the URL FORM (`/shared/static/….png` vs the `/s/<hash>` viewer page) and the access SCOPE. The scope is invisible in the URL, so two links that look identical can behave completely differently.
  - ⚠️ `ensureSharedLink()` SETS access on every call (`PUT {shared_link:{access}}`), so re-running a sync over an existing file upgrades its link — but a file already uploaded under the old scope keeps it until something re-shares it.
  - **The markup sync still uses `"company"`** and is deliberately left alone: the markup files that merge today were shared `open` by a person in Box, so if a tool-uploaded markup ever merges blank, this is the reason and the same one-word fix applies.
