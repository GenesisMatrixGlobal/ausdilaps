# Overview Markup Generator (CLO)

Moved verbatim from the root `CLAUDE.md` §3 on 2026-10-26 so it loads only when working on these files. Project-wide rules (Supabase refs, local dev writes to production, guardrails) stay in the root file.

- **Overview Markup Generator (`closeout-markup`, code `CLO`) — projects + reports (BUILT 2026-09-16).** ⚠️ **Renamed from "Closeout Markup" to "Overview Markup Generator" on 2026-09-18 (Rhys) — the LABEL only.** "Generator" is in the TOOL's name and nowhere else: the thing it produces is a markup, so the Box filename, the download stems and the error messages say "Overview Markup" — same as Cover Photo Generator and Floor Plan Generator. The slug stays `closeout-markup` (a live route and a redirect target), the code stays `CLO`, the save file's `kind` stays `ausdilaps.closeout-markup` (or every file saved before the rename stops opening), and `lib/closeout-markup/*` keeps its name. ⚠️ **References to "the Closeout Markup field" are NOT stale** — `Closeout_Markup__c` is the field's real name in Salesforce and did not change, so the tool is called Overview Markup and writes to the Closeout Markup field. Renamed with the label: the tool card, the Box filename (it defaults to the download name, `<opportunity-slug>-overview-markup.png`, set in `components/tools/closeout-markup/index.tsx` and editable in the send panel), the downloaded `.png`/`.json`/`.csv` stems, and the "isn't an overview markup" / "already has an overview markup" messages. Paste an Opportunity link → it reads the WorkOrders, collapses them into properties, colours each by how its inspections went, draws them, and files the PNG to Box + the link onto `Opportunity.Closeout_Markup__c` (a URL field beside `Closeout_Letter_Link__c`; **zero opportunities had it populated** — this tool is what fills it). Read-only against Salesforce apart from that one field. `lib/closeout-markup/*`, `npm run check:closeout` (pure, fixture = the real `PRE OPT-34851` payload).
  - ⚠️ **Work orders are per UNIT, so group on the COORDINATE, never the address string.** `PRE OPT-34851`: 257 work orders, **254 distinct `Street` values, 42 distinct lat/lngs** → 39 properties. Salesforce geocodes every unit of a building to a byte-identical pair.
  - **`Street` is `<tenancy>, <address>` and the tenancy is not always a number** — `101 , 9 Derwent Street`, `G01 , …`, `Commercial 1, 4-8 Allen Street`, `McDonald's, 799 King Georges Road`, `Gavan Property - GL Shop 1, 803-815 …`. A prefix regex cannot cover that; `addressSegment()` splits on the comma and asks which SEGMENT is the address (the one opening with a house number AND naming a `STREET_TYPES` word — now exported from `lib/property-sizing/parse.ts` rather than copied). ⚠️ **A slash means a unit and the address is on EITHER side** (`1/48-50 Connells Point Road` vs `9 Derwent Street / Suite 1`) — picking by position reduced three tenancies to the streets "1", "2", "3".
  - ⚠️ **Addresses at one point are SUB-GROUPED, never assumed to be one property.** Eight High Street terraces at Barangaroo share a geocode; keeping only the majority took **114 of that job's 125** work orders off the drawing. What a shared point costs is the BOUNDARY, so those are pinned (`sharedPoint` caps precision), not dropped.
  - ⚠️ **A coarse geocode is NOT discarded.** 17 units of 824-828 King Georges Road all came back `GeocodeAccuracy: "City"`; an earlier rule binned every coarse row and lost the building. `Precision` is `precise` / `approximate` / `area` — all are drawn, only `precise` gets a cadastre lookup. A row that is not a street address at all (`Induction`, `Access Letters`, `Wulugul Walk`) is listed under the sheet, never silently dropped.
  - **Colour is from `StatusCategory`, not `Status`** — the Status picklist has 15 years of inactive values still on live records (`Schedule` AND `Scheduled`, `Cannot Complete` AND `Access Failed`). `Completed`→green, `CannotComplete`/`Canceled`→red, everything else→orange. **Per property: one colour present → that colour; more than one → `partial`.**
  - ⚠️ **`partial` is a GREEN OUTLINE + ORANGE FILL, not a fifth colour** (Rhys, 2026-09-16, over a proposed purple). **Not stripes:** `google.maps.Polygon` takes a solid `fillColor` only, so a striped export would not match the live map — preview/export parity. A lot's colour is therefore a `{stroke, fill}` pair (`MARKUP_STYLES` in `style.ts`, replacing the old flat hex map; `markupColor()` returns the stroke for badges/swatches). The key row carries the colour as a two-tone CIRCLE — green centre, orange ring — with the label in plain ink; it was coloured TEXT until 2026-09-17, which Rhys found hard to read (orange worst, and a two-tone status had to be an outlined glyph that muddied the letters). ⚠️ **The on-screen `MapLegend` overlay is GONE (2026-09-17)**, deleted rather than fixed: the counts line above the map already names every colour with the same two-tone dot, and a key box over the imagery that the export no longer draws there is exactly the preview/export drift this tool keeps getting caught by.
  - **Parcels come from the state ADDRESS LAYER first** (`verifyParcelForAddress` with `parcelRing: null`), by text near the point — that is what separates the stacked terraces; the coordinate is the fallback and only for a `precise`, unshared point. **Free and keyless**: Salesforce supplies the coordinate so nothing is geocoded, and only the export's Static Maps tiles are billed. Cadastre covers QLD/NSW/VIC only (~82% of work orders; SA/WA/ACT jobs are all pins).
  - **Hard cap `MAX_CLOSEOUT_LOTS = 60`** and the tool REFUSES over it — the first 60 of 698 in street order is a drawing of one suburb presented as the job. Over the cap nothing is pre-ticked. The sheet and its CSV work at any size (WHT: 1913 work orders → 774 properties).
  - Reuses `MarkupMap` (gained an optional `points` prop for pin-only properties), `useShapes`, `ShapePanel` and `/api/kml/standard-markup/render` (gained `points` and a caller-supplied `legend`, validated against the GENERATED `overlay-paths.ts` label set so an unknown label is a 400, never a blank strip). **Deliberately NOT the shared quote-lines table** — a closeout has no products, rates or m².
  - **The PROJECT SITE, from `Opportunity.Site_Address__c` (BUILT 2026-09-18, `lib/closeout-markup/site.ts`).** The works the job is about, drawn as an **UNFILLED red outline** (`MARKUP_STYLES.site`) so a client sees which properties were inspected AND what caused the job. Measured against the live org before building any of it:
    - ⚠️ **97% populated, 0% GEOCODED** — 1,936 of 2,000 opportunities carry a street, and not one carries a coordinate, because the org's geocoding clean rules run on `WorkOrder.Address` and not on this field. So the site is the **only thing in this tool that spends money**: one Google geocode per address segment (the properties are free — Salesforce supplies their coordinates). Well inside the 10k/month free tier.
    - ⚠️ **Only 72% is a single clean address.** 25% has no house number and is frequently a project NAME in an address field (`Western Tunneling Package`, `Video Inspection`, `Building 17 Refurbishment`); 2% is two addresses (`172-180 Anzac Parade & 116R Todman Avenue`); 1% is an intersection (`Corner Nissen Street & Urraween Road`). Anything without a leading house number is REPORTED, never drawn.
    - ⚠️ **`siteAddressSegments()` splits, and a bare number borrows the street AFTER it.** `1-5 Polding Place, 6 & 12 Sturt Street` is THREE addresses and the middle one is just "6". Geocoding the whole string instead returns one precise-looking hit and draws a third of the site as if it were all of it. Pure, and pinned in `check:closeout` against the real strings out of the org.
    - ⚠️ **Address layer FIRST then COORDINATE, and the coordinate is the branch that usually answers** — the reverse of the properties. A development site's addresses have typically been consolidated into one title and REMOVED from the address layer, which is exactly why it misses them: all three Polding/Sturt segments are absent from it, and the two that geocode both land on lot `7//DP128229`, 9,102 m² — which IS the site (verified: every rooftop segment falls inside that ring). Layer-only found nothing at all on that job. `parcelByAddress()` was extracted from `resolveCloseoutParcels` so both paths share the spans-several-lots rule.
    - ⚠️ **A ROOFTOP-grade geocode only — STRICTER than the shared precision gate**, which lets a `GEOMETRIC_CENTER` through on its `types`. Every other caller can afford that because the address layer checks the answer afterwards; this one has no second opinion, for the consolidation reason above. `12 Sturt Street, Telopea` comes back `GEOMETRIC_CENTER` with a **plus code** in the formatted address, 389 m away, on an unrelated 24,062 m² lot. `geocodeViaGoogle` now returns `locationType` and `plusCode` so a caller can insist.
    - ⚠️ **Deduped on the LOT**: a consolidated site answers several of its own addresses with one title, and drawing it per address double-strokes the outline. The addresses merge into one label.
    - **No pin fallback**, deliberately: a numbered pin means "a property we inspected" here, and the site is neither numbered nor inspected. A site that cannot be placed is reported with its address and the operator draws it — `CLOSEOUT_SHAPE_PALETTE` carries the same unfilled red, so a hand-drawn site is indistinguishable from a found one.
  - ⚠️ **`MARKUP_STYLES.site` is red with `fillOpacity: 0`, and it cannot be plain `red`** — red on a closeout already means "closed, not inspected", so two rows of the key would carry an identical red dot meaning different things (Rhys chose this over Building Markup's solid red, 2026-09-18). Unfilled is the principled distinction rather than an arbitrary one: the site is the WORKS, not a property with a status. ⚠️ **NOT dashed**, the other obvious answer: `google.maps.Polygon` can only dash a stroke via a Polyline's `icons`, so the live map could not match the export — the same reason there are no stripes. Fill opacity is now **per style** and BOTH renderers read it (`style.fillOpacity`), as does the shape picker's swatch and the key's, so an unfilled lot has an unfilled swatch. The live map's lot-rebuild guard had to move from comparing the stroke HEX to comparing the colour KEY: `red` and `site` are both `ff0000`. **The key row reuses the label `"Project Site"`** rather than adding one — `overlay-paths.ts` is GENERATED and regenerating it would change every existing markup's legend, and matching Building Markup's wording is the better answer anyway. **Verified byte-identical through all of it**: Building Markup's export hashes `0ca02d9dc91f801c` before and after.
  - **The summary list is OPTIONAL ON THE EXPORT, and the numbered pins go with it (2026-09-18).** One checkbox — **"Include summary"**, ON by default, sitting immediately BESIDE Download .png, stored in the save file as `includeSummary` (⚠️ read as `doc.includeSummary !== false` so a file saved before the toggle reopens the way it was exported, with the summary). Rhys asked for both on one switch: **a pin's number is only readable against the list it indexes**, so a client handed numbered teardrops and no summary has no way to read the drawing. Off ⇒ `schedule: []` and every `label: ""`.
    - ⚠️ **It governs the EXPORT ONLY, and the POSITION is what says so** — which is what lets the label be two words. It read "Inspection summary (and numbered pins)" first (ambiguous: it sounded like a change to what is drawn), then "Summary list on the exported image (and its pin numbers)" for one revision, and Rhys cut it to "Include summary" and put it next to the download button: spelling it out was answering, in the label, a question the placement already answers. **Move this control away from Download .png and the wording stops being enough.** The map, the sheet and the tick state are untouched.
    - ⚠️ **The LIVE MAP ALWAYS shows its badges** (`numbers`, not `drawnNumbers`) — the ONE place in this pipeline where the preview deliberately shows MORE than the export. A first cut stripped them in step, on the usual parity argument, and Rhys reversed it: the badges on screen are how an operator checks property 4 on the map against row 4 of the sheet, and that job does not stop mattering because the client's copy won't carry numbers. The drift is safe **because the checkbox names the exported image** — the export's contents are the operator's own explicit choice, not something the tool quietly did differently. Don't "fix" this back.
    - The SHEET keeps its own numbering either way: that is the operator's index, not the client's cross-reference.
  - Its own save file (`lib/closeout-markup/file.ts`, kind `ausdilaps.closeout-markup`), not `BuildingMarkupFile`: that one describes a quote. ⚠️ **It stored `shapes: unknown[]` and DROPPED them on open** — nothing parsed or restored them, so a hand-drawn council asset vanished the moment the file was reopened. Fixed 2026-09-18 by extracting `parseSavedShapes()` out of `parseBuildingMarkupFile` and calling `shapes.replaceAll()` on open. The site's resolved rings are stored too, and never re-resolved: that would re-spend a geocode AND could hand back a different parcel from the one signed off.
  - `lib/salesforce.ts` gained `soqlQueryAll()` (⚠️ `soqlQuery` stops at 2,000 and the biggest opportunity is 1,913 — a truncated work-order read under-reports a job with nothing on screen to say so) and a 10-minute access-token cache. `lib/salesforce-links.ts` holds `parseSalesforceRecord()`, extracted from `parseQuoteLookup` which now delegates to it (verified behaviour-identical on 10 inputs incl. the `ausdilaps--dev` host).
