# Staff portal + Command Centre

Moved verbatim from the root `CLAUDE.md` §3 on 2026-10-26 so it loads only when working on these files. Project-wide rules (Supabase refs, local dev writes to production, guardrails) stay in the root file.

- **Staff portal (BUILT — don't redo):** `/staff` = per-user magic-link auth, department-scoped. `/admin` = company admins only. See `docs/staff-portal.md`.
  - Five departments in `lib/departments.ts`: estimators, inspectors, projects, reports, accounts (labelled "Admin & Accounts" — the old separate `office` department was merged into it). Stored as `profiles.departments text[]`; `admin`/`superadmin` implicitly get all.
  - Auth surface is `lib/auth/session.ts` (`getStaffUser` / `requireStaff` / `requireDepartment` / `requireAdmin`). `proxy.ts` refreshes the Supabase session and does the coarse signed-in check; role/department checks live in the layouts.
  - `/staff/[department]` presents two tabs: **Tools** and **Training**, as parallel-route slots (`@tools` / `@training`) with `DepartmentPanes` hiding the inactive one. Both panes stay mounted, so toggling tabs never throws away what a tool was holding. `DepartmentTabs` remembers each pane's last URL — point the Tools tab back at the bare `/tools` list and the return trip unmounts the tool anyway, defeating the whole arrangement.
  - `/staff` redirects a non-admin with exactly one department straight to it. Admins keep the list.
  - **Tool registry** `lib/tools/registry.ts` — tools are department-agnostic components in `components/tools/*`. ⚠️ **The registry is METADATA ONLY (2026-10-07):** the components are mapped by slug in `components/tools/tool-components.tsx`, a client module imported only by the tool page (Tender Watch, the one server tool, is imported there directly). With components in the registry, every page importing it — `/admin`, `/staff`, the tools list — shipped every tool, ~890KB of entry JS (256KB gz); now ~80KB. Adding a tool = a registry entry + a line in that map; `npm run check:registry` asserts the two agree. Surfacing a tool to another department = adding a slug to its `departments` array. **A GAME is `kind: "game"` with NO `departments` field** — `ToolDefinition` is a discriminated union so writing one is a type error — and it appears under a "Games & Activities" heading on EVERY department page. ⚠️ Not `departments: []`: `/admin/tools` builds a link from `departments[0]` (→ `/staff/undefined/...`) and `departments.includes()` is false for an empty array, so a game would show under NO department. Read `departmentsFor(tool)`, never `tool.departments`, wherever both kinds are handled. Games are excluded from `toolsForDepartment()` (keeps the `/staff` "N tools" count honest) and from the `/admin` "Tool uses" headline (or break-room plays would imply the estimating tools are busier than they are). **None of this touches the database** — the tool→department mapping is code-only and `tool_usage` has no department column. Never copy a tool. Each tool has a permanent `code` (SMK, PSZ, RSE, TDW, FPL, KML) for referring to it in conversation — **never renumber or re-letter one**, it would silently invalidate every past discussion. **Titles are display labels and do get renamed; slugs and codes never do** (a slug is a live route and a redirect target). Current divergences, all deliberate: `site-markups` = "Quote Builder", `property-sizing` = "Bulk Property Sizing", `road-survey-estimator` = "KMZ Analyser", `floor-plan` = "Floor Plan Generator", `closeout-markup` = "Overview Markup Generator".
  - **Training** = MDX in `content/training/<department>/*.mdx` via `lib/training.ts` (mirrors `lib/insights.ts`).
  - **`/admin` is labelled "Command Centre" in the UI (2026-09-24, Rhys) — the route stays `/admin`.** In its header the AusDilaps LOGO goes to the website (`/`) and the orange "Command Centre" label goes to the overview. The staff header's link is "Command Centre" and shows at every width (it was hidden below `sm`). **The website header shows a "Command Centre" link to a signed-in admin** (`components/marketing/command-centre-link.tsx` → `GET /api/staff/me`, one boolean, `no-store`): client-side so marketing pages stay static/ISR, and it only asks when an `sb-…-auth-token` cookie exists, so an ordinary visitor costs no request.
  - **Command Centre speed (2026-10-08).** Rhys reported it "really slow". What was measured, and what each fix is for — read before "optimising" any of it:
    - ⚠️ **`app/admin/loading.tsx` gives instant click feedback; it does NOT change tab prefetching.** Sibling-tab prefetches on this non-PPR app are a route-tree + metadata-only request and never ran a page loader, before or after. Keep AdminNav on the DEFAULT prefetch: `prefetch={true}` renders all seven pages on every load, `prefetch={false}` makes clicks wait for the server. The cached route tree goes stale after ~5 min, so the tabs, both headers' links, the website's Command Centre link and the API usage month arrows carry `<LinkPending>` (NOT yet the overview's tile and alert links) (`components/staff/link-pending.tsx`, `useLinkStatus`): an always-rendered orange dot that fades in after 120ms on ANY click, cached or not.
    - ⚠️ **`experimental.staleTimes.dynamic = 30` is APP-WIDE.** A Link back to any dynamic page within 30s reuses the old render. Only `router.refresh()` or a revalidating server action clears it — a `fetch()` to a route handler does not. Any client view seeded from server props that mutates through `/api/*` must `router.refresh()` after a successful write (Tender Watch does; a sent tender reappeared in the queue before it did).
    - ⚠️ **`web_vitals.ttfb_ms` is NOT server time.** Vercel answers every HTML request with an empty HTTP 103 first, and web-vitals' TTFB is that arrival — ~50ms regardless of how long the server took. The real figures are LOGGED by `/api/vitals`, never stored: `[vitals] load /admin server=…ms html=…ms` (hard loads on /admin and /staff, from the navigation entry's `finalResponseHeadersStart`) and `[vitals] nav /admin/staff …ms (…, skeleton|no skeleton, gave up?)` (Command Centre tab clicks, start = `instrumentation-client.ts` `onRouterTransitionStart`, end = route committed AND the loading skeleton gone — `components/staff/nav-timer.tsx`). Read with `npx vercel logs ausdilaps.com.au --query "[vitals]"`. ⚠️ A nav beacon returns before the database by design. ⚠️ The nav timer finds the skeleton by `[role="status"][aria-label="Loading"]` — change `loading.tsx`'s root markup and every slow tab silently reads as instant. ⚠️ Never read `onRouterTransitionStart`'s third argument: it is null unless an experimental flag is set.
    - **PageSpeed lab scores are a NIGHTLY CRON, not a request-time call** (`/api/pagespeed`, `0 16 * * *` UTC = 2am Brisbane, `CRON_SECRET`, writes `pagespeed_scores` via migration `0030`; `/admin` only reads two rows). The old `unstable_cache` keyed on the MINIFIED callback text, so the "24h" cache reset on many deploys and the first open after one ran two live Lighthouse calls (10-40s) in front of the page — the most likely cause of "really slow". A failed run keeps the last good scores (writes only label/error/checked_at), and a 200 with no Speed score counts as a failure. To get scores without waiting for 2am: Vercel → Settings → Cron Jobs → Run on `/api/pagespeed`.
    - **The DB was never the problem** (all overview queries ~100ms). What remains on a first open after a break is a cold function plus the proxy's and layout's auth round trips ahead of the shell (~1.4s blank, measured from field FCP by idle gap) — measure with the log lines above before changing anything.
  - `/admin/staff` invites staff (Supabase `inviteUserByEmail` + the `0005` `auth.users` trigger) and assigns departments, via server actions that each re-check `requireAdmin()`.
